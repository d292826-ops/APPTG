# Бот записи на встречи

Новая локальная версия @FinDir41bot по документу «Техническое задание.md». Исходный финансовый помощник находится в соседней папке `findir-bot` и не изменён. Для одного Telegram-токена должна работать только одна версия.

## Начальные настройки

- Понедельник–пятница, 09:00–18:00, Asia/Kamchatka.
- Запись минимум за 24 часа, на 30 дней вперёд.
- До 4 встреч бота в день, включая ожидающие заявки; чужие события календаря ограничивают свободное время, но не дневной счётчик.
- Длительности: 15, 30, 45, 60, 90 минут. Время начала — в :00 или :30.
- Буферы выключены; срок решения — до начала встречи, но не более 48 часов.
- Изменение расписания не отменяет существующие встречи автоматически.
- При переносе прежняя встреча остаётся до согласования нового времени. Блокировка отклоняет ожидающие заявки, но сохраняет согласованные встречи.
- Закрытые заявки и логи хранятся 30 дней. Активные заявки и сохранённая почта пользователя сохраняются.

## Управление на Mac

Откройте Терминал в этой папке:

```sh
./manage.sh start
./manage.sh status
./manage.sh stop
./manage.sh test
./manage.sh check
```

Исходный код и тестовое окружение находятся в этой папке проекта. Рабочая копия службы расположена в `~/Library/Application Support/GoogleBot`: там находятся своё окружение `.venv`, секреты `.env`, база и журналы в `data`. Это позволяет macOS запускать службу без доступа к защищённой папке Desktop. Изменения исходного кода не попадают в рабочую копию автоматически: перед обновлением службу нужно остановить, скопировать изменённые Python-файлы и запустить снова. Файл `requirements.txt` описывает зависимости. Для воспроизводимого установленного окружения используется `requirements.lock.txt`.

Компьютер должен быть включён, подключён к интернету и не спать. Команда `start` не настраивает автоматический запуск после перезагрузки macOS.

## Назначение администратора

До назначения администратора заявки не принимаются. При первом запуске создаётся одноразовый код в `~/Library/Application Support/GoogleBot/data/admin_claim.txt`, доступный только локально. Владелец должен отправить в личный чат с ботом `/claim КОД`. Не публикуйте эту команду в учебной группе. Код удаляется после успешного назначения; бот пытается удалить сообщение с кодом. Повторное присвоение роли через `/claim` запрещено.

Команда `/id` показывает ID текущего пользователя. `/admin` открывает админку назначенному владельцу. Роль проверяется на серверной стороне при каждом административном действии.

## Подключение Google Календаря

Для прямой работы бота нужен OAuth-клиент Google, одного подключения Google к ChatGPT недостаточно.

1. Откройте [Google Cloud Console](https://console.cloud.google.com/), выберите или создайте проект.
2. Включите Google Calendar API в библиотеке API.
3. В Google Auth Platform настройте приложение и аудиторию. Если приложение в режиме Testing, добавьте свой Google-аккаунт в тестовые пользователи.
4. Создайте OAuth client ID типа **Desktop app**, скачайте JSON. Сохраните его в рабочую папку службы под именем `~/Library/Application Support/GoogleBot/data/google_client.json`. Не публикуйте JSON и не добавляйте его в репозиторий.
5. Выполните `./manage.sh google`. Откроется Google в браузере. Самостоятельно войдите в аккаунт владельца календаря и разрешите доступ.
6. Выполните `./manage.sh check`. Проверка должна сообщить, что доступ к календарю проверен.

В `.env` рабочей копии по умолчанию указан `GOOGLE_CALENDAR_ID=primary`. Для другого календаря укажите его идентификатор и перезапустите бота.

Запрашиваются права чтения календарей и редактирования событий. Бот работает с выбранным календарём, а не получает доступ к календарям гостей. Гость приглашается по email; появление события в его календаре зависит от настроек приглашений. События создаются с Google Meet и напоминанием за час.

Внешнее OAuth-приложение в режиме Testing может требовать повторной авторизации через 7 дней при используемых календарных разрешениях. При утрате доступа повторите подключение; бот не подтверждает встречи при ошибке Google.

Официальные инструкции: [Python quickstart](https://developers.google.com/workspace/calendar/api/quickstart/python), [создание событий](https://developers.google.com/workspace/calendar/api/guides/create-events), [сроки refresh token](https://developers.google.com/identity/protocols/oauth2#expiration).

## Проверка домашнего задания

Автоматические тесты проверяют бизнес-логику с подменой календаря. Они не доказывают, что реальный аккаунт Google уже подключён.

После подключения:

1. Назначьте администратора и проверьте `/admin`.
2. С другого Telegram-аккаунта отправьте тестовую заявку на реальный свободный интервал и собственную тестовую почту.
3. Согласуйте её из админки. Проверьте событие, Meet, почтовое приглашение, отсутствие дубля при повторном нажатии.
4. Отдельно проверьте отказ, истечение срока, отмену, перенос, блокировку и ограничения расписания по критериям ТЗ.
5. Сделайте скриншот настоящего диалога с меню и подтверждённой встречей, скрыв личную почту при необходимости.

Текст для сдачи после полной проверки: «Урок 6.5 — разработал бота по своему ТЗ, запустил локально и проверил работу». Приложите скриншот. Публикация выполняется владельцем.

## Ограничения и восстановление

- Пока Google не подключён, меню доступно, но бот не показывает выдуманные свободные слоты.
- Намерение создать или отменить событие сохраняется до запроса Google. Незавершённые операции повторяются после сбоя; идентификатор события остаётся прежним.
- Календарь проверяется непосредственно перед созданием события. Полностью исключить ручное создание пересекающегося события владельцем между проверкой и записью Google Calendar API не позволяет; календарь не предоставляет транзакцию резервирования.
- Уведомления сохраняются и повторяются при временной ошибке. При неизвестном результате отправки возможен повтор уведомления; дубли событий предотвращаются отдельно.
- Журналы содержат коды ошибок без токенов и содержимого сообщений.
- Автоматические резервные копии и Mini App в первую версию не входят.
